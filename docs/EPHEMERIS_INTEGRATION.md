# VirgoStars-Ephemeris mobile integration

Status: **experimental prototype**, not numerical or release parity. The default Rust build uses the CPAL-1.0 VirgoStars-Ephemeris core at revision `6835e00e4b4ba5fc52d882a793e2dfa2b2a436aa`. The native adapter derives from VirgoStars Desktop commit `023d76d`; desktop attribution and third-party terms remain applicable. No kernel or USNO/Chiron file is committed or bundled, and distribution rights and packaging are not established.

In **Options → DE441 ephemeris data**, select an independently obtained classic DE441 binary using the system file picker. Select a newer compatible binary in the same place to update it. The app copies the selected file in 64 KiB blocks into its private data directory, displays progress, allows cancellation and checks the header, declared size and several records/required planetary series before atomic replacement. It keeps the previously installed file when an update is cancelled or rejected. The engine reloads on the next calculation; already displayed/session charts must be recalculated to reflect the new data. Up to 8 GiB is accepted, and updating requires enough free space for both copies. Technical checks are not a trusted checksum or authentication; obtain data from a trusted source and check its distribution rights independently. There is no automatic download or background update.

In the same settings section, select `deltat.data` and `historic_deltat.data` together, optionally adding `deltat.preds`; filenames must match exactly. For an update, select the complete new set again. Without the predictions file, the table ends at its last observation; if supplied, predictions must include usable points after the last observation. Each input is limited to 4 MiB. The app validates the combined continuous series with the shared core and atomically replaces the previous set as one bundle; an incomplete, inconsistent or cancelled update leaves the old set in place. The displayed table dates describe the source data: the current time policy starts at 1900 and is further limited by DE441 coverage.

For Chiron, select a compatible JPL type 21 small-body SPK of at most 32 MiB. The core checks its format, target 2060 Chiron, heliocentric centre (NAIF 10, Sun) and a sample state before replacement. Coverage is shown as TDB dates; Chiron is unavailable outside its file's coverage. The engine reloads imported USNO and Chiron on the next calculation, and existing charts should be recalculated. All checks are structural and do not establish authenticity or scientific accuracy; no files are downloaded or provided by the app.

The app-managed files (`ephemeris/de441-imported.eph`, `usno-imported.bundle`, `chiron-imported.bsp`) take priority over older host-side configuration, so the data selected in the app is used. Otherwise the host searches environment variable, optional `ephemeris.json` in the native application local-data directory, `ephemeris/` in that directory, then `ephemeris/` in the native resource directory. The legacy expected names are `de441-slice.eph`, `usno/deltat.data`, `usno/historic_deltat.data`, optional `usno/deltat.preds`, and optional `chiron.bsp`. The DE441 binary must be a classic DE441 file accepted by the core; an arbitrary BSP is not a substitute. Environment variables are `VIRGOSTARS_DE441_PATH`, `VIRGOSTARS_USNO_DIR` and `VIRGOSTARS_CHIRON_SPK`; configuration keys are `de441`, `usnoDirectory` and `chironSpk`. Paths are host-controlled and never accepted from the WebView.

The data status screen reports the actual selected DE441, USNO and Chiron files, including local desktop-compatible files, rather than only app-managed imports. On 2026-11-18, verified desktop files were copied to a connected Pixel 8 Pro's previously absent private ephemeris directory. A native current-time calculation at fictional coordinates succeeded on that device; after the debug app was updated, the current-sky canvas was visible on its home screen and all three data sources reported available. This one-device setup does not put data in future APKs or installs.

Absent or unreadable DE441, or a configured USNO directory whose required tables cannot be parsed, makes the provider unavailable. Without USNO tables the core's narrower civil-time policy applies. Coverage is the intersection of that policy and the actual DE441 file; dates outside it report `out_of_range`. An absent or unusable Chiron SPK reports Chiron unavailable. The provider is not silently replaced by Swiss. Explicitly enabling the local-only `swiss-ephemeris` Cargo feature selects Swiss instead; it remains subject to the rights restrictions in [the Swiss prototype note](SWISS_LOCAL_PROTOTYPE.md).

The native provider returns apparent geocentric positions and modelled lunar points. Mars through Pluto refer to planetary-system barycentres; Chiron needs the external small-body SPK. Astronomical angles and their UTC-as-UT1 approximation, time source and observer are explicit in the versioned payload. The five house systems are computed by `astrological-functions` from those angle facts; failures are listed per system without substituting another method. Kernel identity is not verified by a trusted manifest and must not be represented as verified provenance.

Local host tests with a desktop-supplied DE441 slice and USNO/Chiron files checked reference values for Sun, Moon and Jupiter at J2000, time-policy decisions, a polar request and luminary access. Contract tests use synthetic inputs. On 2026-11-17, an Android 36.1 x86_64 emulator debug build was tested by WebView DOM events: absent data produced `provider_unavailable`, a temporarily supplied desktop DE441 slice produced a rendered fictional J2000 chart with five house systems, and a date outside the time policy produced `out_of_range`. The temporary kernel, debug forward and emulator were removed or stopped after testing; no data was bundled or binary published. These are local checks, not independent cross-engine validation, complete scientific accuracy, performance, iOS or physical-device verification. `astrological-functions` and the chart renderer currently come from sibling checkouts and their distribution rights also need review.

An additional Android emulator smoke used the system document picker to import a locally supplied 20.6 MB DE441 slice, calculated a fictional chart, restarted the app and calculated again, then replaced the managed file with a valid file and recalculated. A separate invalid-file update was rejected while the previous kernel remained usable. The native picker was selected with emulator input and the WebView was controlled through debugging; this does not establish physical-device touch, very large file performance or recovery under actual power loss. Test files were removed and the previously existing emulator file was restored.

Another local Android 36.1 x86_64 emulator smoke used the system picker to select the three locally supplied USNO files together and a 3.7 MB Chiron SPK, then checked a fictional J2000 chart with Chiron and a 2027 chart using predicted ΔT. Both calculations worked after an app restart and after selecting valid replacement data. Rust tests with the same external data separately checked rejection of invalid replacements while retaining the previous USNO bundle and Chiron SPK. Test files were removed; this is not physical-device, large-SPK, independent scientific or power-loss validation.
